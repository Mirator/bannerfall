## Evidence and correction sketches

### 1. Expired party timers can erase the campaign on reload

`World.updateParties()` subtracts `dt` from positive `waryT` and `clashT` without saturating at zero (`src/world.js:932–934`). `persistParties()` serializes them with `p.waryT || 0` / `p.clashT || 0` (`:308`), which preserves negative numbers. The validator requires nonnegative timers (`src/save.js:233`, `:239`), and `SaveRepository.#parseCampaign()` queues removal of a rejected save (`src/persistence/save-repository.js:30`). Ordinary cooldown expiry therefore crosses a destructive persistence boundary.

Chromium reproduction: create the production world with seed 7, set a live party's ordinary cooldowns to 25 and 6 seconds, run `updateParties(1/60)` 1,600 times, and call `syncLiveStateToSave()`. Timers become `-0.01666666666652956` and `-0.016666666666650353`; `parseSave(JSON.stringify(save))` returns null. Clamping only the serialized timers makes that same save valid. The source establishes the subsequent deletion path; the probe did not intentionally delete a real user's save.

Saturate the countdowns and add a real save/reload regression after expiry. Also consider a narrowly bounded normalization for negative timers already written by this release; simply fixing future writes leaves existing affected campaigns rejected. Follow the repository's migration rules rather than relaxing unrelated validation. Verify save-schema, campaign-persistence, release cache, and full gates.

### 2. Absorbed occupiers leave permanent phantom occupation

`campVictoryExtra()` rehomes parties from the razed camp to the stronghold (`src/world/settlement-interactions.js:160–162`). After the last linked camp falls, the absorption loop accepts any fitting stronghold-homed party, including one with `occupying`, and filters it out of `save.parties` (`:188–198`). It never clears the corresponding settlement record's `occupied` flag.

Production-function reproduction: c1/c2 razed, c3 being razed, a one-bandit c3 party occupying Ashford, a one-bandit stronghold garrison, and encounter base 8. After the callback, the party list is empty and the garrison has two bandits, while Ashford remains occupied. There is no remaining occupier to challenge to restore service.

Either keep occupiers deployed or make withdrawal release occupation explicitly; preserve permanent ownership/spec and capture counts. Extend the existing remnant-ceiling test with an occupier and inbound raider. Run regional-campaign and campaign-persistence coverage plus the full gate.

### 3. The save-warning test checks a field, not a warning

`Game.reportSaveFailure()` assigns `saveWarning` and invalidates (`src/main.js:176–180`), but no production renderer reads that field. `tests/e2e/platform-boundary.spec.js:19–27`, titled “storage failure becomes a player-visible warning,” checks only the internal property.

Chromium reproduction: reject `platform.storage.write`, call `persistRun()`, await settlement, instrument canvas `fillText`, and call `game.draw()`. `saveWarning` contains the intended sentence; no warning text is drawn. The pause screen can still claim the campaign is saved.

Render a persistent warning across relevant scenes, define when successful persistence clears it, and test actual rendered output. Preserve the existing no-unhandled-rejection behavior. Run platform-boundary and visual/full gates as appropriate.

### 4. Owned targets bypass the settlement floor

`updateRegionalPressure()` uses `neutral.length > 1` only when `held.length === 0` (`src/world.js:1406–1418`). A nonempty held list is eligible even when every other settlement is already occupied. On arrival with the hero absent, the raid may occupy that last site (`:952–960`).

Production-method reproduction with Ashford owned and serviceable, the other three sites occupied, and expired cadence dispatches a raid to Ashford. This state is reachable by letting three neutral sites fall, then claiming the remaining free site. The existing floor regression at `tests/e2e/regional-campaign.spec.js:800` covers the zero-owned-land case only.

Apply the reservation floor across held and neutral serviceable sites before choosing a target, while preserving preference for held land. Add the mixed-ownership case to regional-campaign coverage.

### 5. A denied read aborts bootstrap before any usable UI

`SaveRepository.initialize()` uses one `Promise.all` for campaign, test-campaign, and settings reads (`src/persistence/save-repository.js:17`). Any rejection escapes the awaited initialization before `Game` exists (`src/main.js:1638`). The outer catch only logs an error (`:1659–1660`).

In isolated Chromium, making `Storage.prototype.getItem` throw `SecurityError` before navigation produced `booted: false`, an untouched 300-pixel default canvas backing width, no body text, and the initialization console error. Existing tests make storage throw after successful boot, so they miss this path.

Provide a visible startup recovery/error state. A playable temporary-storage mode is an optional product decision, but do not silently classify an unreadable existing campaign as absent or overwrite it. Add a pre-bootstrap read-rejection browser case and verify independent slot failures.

### 6. Palisade placement crosses the RNG boundary

`placeCamp()` takes `rng` and `fxRng`, but computes shared plank/collider positions from `fxRng` (`src/battle/terrain.js:325–328`). Varying only the FX seed in production `buildTerrain()` changes all six physical palisade colliders. The current effects-disabled test does not cover this: disabling effects does not substitute a different FX stream.

Use the gameplay terrain stream for coordinates consumed by collision; retain FX randomness for purely visual properties. Add a geometry-invariance test that changes only the FX stream. Expect a legitimate seeded-geometry change, requiring full, performance, visual, and relevant balance verification; do not automatically accept changed screenshots.

### 7. Intro FOLLOW is not remembered as deliberate

Intro processing calls `updateCommandPhase()` (`src/battle.js:526`). Deliberate-order bookkeeping records only `state === 'deploy'` (`:476`). `confirmDeploy()` then promotes unrecorded FOLLOW to HOLD (`:651`). For a clearly acknowledged reproduction, issue CHARGE and then FOLLOW during intro, enter deployment, and confirm: the final order is HOLD.

Record explicit pre-fight orders consistently across intro and deployment, retaining idle default HOLD promotion. The existing QA checks intro CHARGE, which survives because only FOLLOW is promoted. Add separate untouched-default and explicit-FOLLOW cases.

### 8. Claim route selection mistakes a refusal for an unvisited destination

`claim()` returns on a disabled claim row without recording the destination as attempted (`tests/e2e/campaign-harness.js:466`). `nextUnclaimed()` excludes owned sites only (`:542–550`), and `claimRush` calls it four times (`:580–583`). After spending 60 of the starting 80 gold on one village, the nearest unaffordable site remains nearest and can consume all remaining route steps. The mixed policy uses the same selection (`:599`, `:602`).

This is a harness defect, not a claim-cost defect. Track route attempts separately from ownership and specify whether later stages retry earlier refusals. Assert visited destinations, then remeasure the campaign sweep before using its comparisons to retune gameplay. No revised win rates are claimed in this audit.

### 9. Reserve-wave loot excludes the reserve

`updateObjectivePhase()` increments `totalEnemies` when a wave actually arrives (`src/battle/objectives.js:109`), but `endBattle()` now pays only `lootFor(battle.setup.enemies)` (`src/battle/combat.js:138`). A production-module probe with an initial bandit and an arrived brute paid 10 rather than 36. The existing wave test only asserts positive loot (`tests/e2e/battle-objectives.spec.js:580`).

Track the types actually deployed, including arrived reserves, and calculate the same type-based reward over that roster. Do not pay pending waves that never arrived. Current production waves belong to the finale, so the practical effect is primarily final reward/accounting, not a mid-campaign recovery deficit.

### 10. Squad deaths leave the aggregate command stale

`aggregateStance()` considers surviving squads (`src/battle.js:444–456`), but removing the last member of a squad does not refresh the stored mirror (`src/battle/combat.js:87–98`). With spear HOLD and archer CHARGE, killing the archer leaves `battle.command === 'mixed'` while `aggregateStance() === 'hold'`.

Movement still reads per-squad stance correctly. Refresh the aggregate at roster removal and cover the published state in the squad regression. This is lower priority than player-facing order failure.

### 12. Current guidance contains contradictory historical claims

`tests/README.md:69` and `.github/workflows/balance-sweep.yml:4` still say the stance sweep carries `test.fail()` and cannot fail on gameplay changes. Its annotation was removed, as recorded in `tests/e2e/stance-balance.spec.js:361`. `tests/README.md:112` also describes campaign criterion 3 as an expected failure at 9/12, while `tests/e2e/campaign-arc.spec.js:135` documents its hard guard. The README save-compatibility section still calls version 4 current; `src/save.js:31` declares version 5.

Update current guidance to match executable contracts. Keep historical measurements explicitly historical. Documentation cleanup does not justify weakening any assertion.
